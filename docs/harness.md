# Quality harness

This repository uses a local, source-upload-free quality harness for long unattended changes. The accepted implementation scope is controls A–F below. The five workflow practices proposed during the audit are deferred; this harness creates no product specification, change-history contract, live agent evaluation, hosted service, or remote repository setting.

The harness was designed from revision `cb5ca28` on 2026-09-12. The pre-change baseline passed type checking, 485 tests in 39 files with zero skips, all three workspace builds, and byte-for-byte plugin regeneration. A stricter TypeScript probe found 56 diagnostics before remediation. Those figures describe the starting revision, not the final harness result.

## Commands and policies

| Command                | Purpose                                                                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm verify`          | Transitional local gate: types, format, static/structure checks, V8 coverage and changed lines, build, plugin freshness, browser journey, security scan, and scanner probes |
| `pnpm verify:strict`   | The same gate with strict static and strict coverage thresholds; expected to fail while recorded legacy debt remains                                                        |
| `pnpm verify:full`     | Transitional gate plus selected-scope mutation testing                                                                                                                      |
| `pnpm test:harness`    | Harness contract and negative-gate tests                                                                                                                                    |
| `pnpm test:e2e`        | Chromium shipped-plugin, persistence, keyboard, and axe journey                                                                                                             |
| `pnpm security:setup`  | Download and checksum-verify pinned local security tools under ignored `.tools/security`                                                                                    |
| `pnpm security:update` | Refresh the local OSV advisory database; network access is limited to this explicit update step                                                                             |
| `pnpm security:check`  | Run secrets, source, and dependency checks without uploading source or dependency metadata                                                                                  |
| `pnpm security:probe`  | Prove secret and dangerous-code fixtures fail without printing fixture secret values                                                                                        |

The strict policy is 95% statements, lines, and functions; 90% branches; and 95% changed executable lines against an explicit merge base. A missing base or report fails. Complexity and cognitive complexity are limited to 15 per function, nesting to four, parameters to five, and functions and test helpers to 80 nonblank, noncomment lines. Mutation testing has an 80% break threshold in its selected scope.

The transitional policy is an explicit implementation assumption because the accepted bounded cleanup may not remove all existing static and coverage debt. It records per-file legacy coverage floors and rejects regression; every new source file must meet 95% statements, lines, and functions and 90% branches. Setup-only changed-line exceptions may cover original tracked production files modified during the harness migration that remain below 95%. Each exception is tied to merge base `cb5ca28` and the exact SHA-256 of the resulting file, so any later content change invalidates it and restores the 95% changed-line gate. The exact exception manifest is also SHA-256 pinned in the executable coverage check: editing baseline JSON cannot add an exemption or rotate its base. Changing the checks themselves remains within the author’s writable scope, so this is not a security boundary against a malicious author. No glob exclusion applies. This leaves a stated risk that setup-modified legacy branches are not fully exercised. `pnpm verify:strict` applies the raw 95% changed-line rule without these exceptions and remains failing until all strict targets pass. Baselines and exception hashes must not be regenerated merely to make a change pass.

`pnpm test:coverage` includes maintained `packages/*/src/**/*.{ts,tsx}` and `scripts/**/*.mjs`, including files not imported by tests. Declarations, tests, generated bundles, dependency directories, coverage output, reports, and tool caches are excluded according to their role. Typed ESLint covers package source; the common mechanical budgets cover JavaScript, MJS, TypeScript, and TSX. Dependency-cruiser rejects cycles, unresolved imports, web imports from server/skill, server imports from web/skill, and production imports from tests. Knip owns unused-file/export/dependency reporting with declared script, package, test, and configuration entry points.

The static abstraction rule is Q-ABSTRACTION: coordinating functions should read as substantial, purpose-named steps; cohesive lower-level functions should own SQL, protocol, serialization, and similar mechanics; simple guards and control flow should remain inline; trivial forwarding extractions should not be added to satisfy a number. For each changed function, review whether its statements operate at a consistent level of abstraction and preserve query scope, ordering, parameterization, and transaction boundaries. Mechanical complexity is evidence, not proof of good decomposition. Checks and assertions must not be weakened to finish a task.

The code-quality rule is **Q-ABSTRACTION: keep each function at a consistent level of abstraction**. A coordinator calls purpose-named operations for substantial mechanics; cohesive lower-level functions may contain their own SQL, protocol details or conversions. Simple argument passing, guards and straightforward control flow may remain inline; avoid trivial forwarding chains. Ask whether a reader can understand a changed function’s sequence without mentally implementing its substantial steps. This is semantic review guidance; complexity/import checks do not prove it. Existing violations are bounded debt, not an automatic architecture rewrite. No new mandatory independent-review workflow is enabled.

## CI, freshness and maintenance

CI installs frozen pnpm dependencies, checksum-verified Linux scanner tools, fresh offline advisories, Chromium, and real TypeScript/Python/Java indexer prerequisites. It runs the same `pnpm verify` entrypoint with full Git history and the PR’s base SHA or push’s previous SHA. The PR job has a 15-minute timeout; its cold hosted duration is unverified. Action references are upstream-verified immutable commits and the token has `contents: read`; verification artifacts upload even after failure. Scanner caches contain downloads/wheels rather than interpreter-bound virtual environments.

The ordinary Ubuntu CI job runs on every pull request and push to `main`, and also runs selected mutation tests when their source, tests, or configuration change. Superseded PR runs are cancelled. Verification artifacts are retained for seven days.

To fit the owner's GitHub Free private-repository budget, the Monday schedule runs only one Ubuntu security job at 03:17 UTC (06:17 Finnish summer time / 05:17 winter time). It refreshes offline advisories, scans secrets/source/dependencies, and verifies scanner negative probes. It uses the existing shell entrypoints without installing pnpm dependencies, browsers, or indexers. Its timeout is 15 minutes, duplicate runs are cancelled, and results remain in the Actions logs without an additional artifact upload. It can also be dispatched manually.

The full workflow is manual-only, intended for pre-release verification: `pnpm verify:full` on Ubuntu with a 60-minute ceiling, plus shipped-CLI smoke jobs on Ubuntu/Node 22.13.0 and macOS/Node 24 with 15-minute ceilings each. All its artifacts are retained for seven days. It no longer duplicates ordinary PR checks or runs on Mondays. The full browser/accessibility/visual journey remains in ordinary Linux CI. This owner-approved scheduling adjustment saves hosted minutes but leaves minimum-runtime/macOS regressions undetected until a maintainer dispatches full verification; revisit before release or if platform regressions become frequent. No automatic release trigger or remote billing setting is added. Hosted durations, costs, and platform execution remain unverified; job timeouts are ceilings, not usage estimates.

Mutation evidence is current for seven days and must be rerun locally or through manual full verification when stale, and after changes to coverage/glob implementation, their tests or Stryker configuration. Offline advisory data expires after seven days. No live model evaluations or model costs are introduced.

All selected tools run locally without paid/private-repository service requirements. Licenses from installed package metadata: ESLint/typescript-eslint/Prettier/dependency-cruiser/Vitest/fast-check MIT; Knip ISC; SonarJS LGPL-3.0-only; Stryker and Playwright Apache-2.0; axe integration MPL-2.0. They are development tools, not additions to the shipped runtime bundles. Typed ESLint complements TypeScript; dependency-cruiser covers architectural relationships and Knip covers unused code; Vitest V8 matches the existing 3.2.6 runner instead of replacing it. Hosted CodeQL/source-upload services and live agent evaluation tools were not selected within the local-only scope. The lockfile and pinned tool setup, not floating latest versions, define reproducibility.

## Deferred workflow practices and remaining gaps

All five proposed workflow practices are deferred: coding-agent regression evaluations; an intent-to-evidence product documentation contract; mandatory independent semantic review; a formal learn-from-failures process; and periodic usefulness/telemetry review. Existing tests and Q-ABSTRACTION still require ordinary implementation review, but no new workflow policy or product spec/history files are part of this change. Revisit these practices only through a separate explicit decision with model budget, ownership, and maintenance cost identified.

Before treating the harness as remotely enforced, inspect hosted workflow execution and its machine-readable reports. Separately verify the repository-host settings, workflow execution, immutable Action references, token permissions, required checks and bypass policy. Current local evidence cannot answer those remote questions. Other bounded gaps are Python advisory coverage, Semgrep rule completeness, mutation scope outside two pure modules, cross-platform artifact execution beyond the currently exercised platform, and external host/indexer compatibility.
